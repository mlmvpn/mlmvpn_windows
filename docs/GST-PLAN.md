# برنامهٔ پیاده‌سازی «تونل گوگل اسکریپت» (GST) در نرم‌افزار ویندوز

سند طراحی — نسخه ۱ — ۱۴۰۵/۰۴/۲۹

---

## ۱) خلاصهٔ بررسی

### ۱-۱) نرم‌افزار ویندوز خودمان (`G:\ip scanner`)
- Electron: [main.js](../main.js) سرور Express محلی ([server.js](../server.js)) را بالا می‌آورد و `public/index.html` را لود می‌کند.
- هر فیچر = یک ماژول بک‌اند در ریشه + یک کامپوننت در `public/components/` + یک `<div id="ls-XXX">` در سایدبار + یک آیکون در activity-bar (خط ۱۰۹۹ `index.html`).
- اعتبارنامهٔ Cloudflare (Global API Key + Email) از قبل در [cloud-manager.js](../cloud-manager.js) پشتیبانی می‌شود (هدرهای `X-Auth-Email` / `X-Auth-Key`) و در `data/cloud-accounts.json` ذخیره است. `deployWorker()` هم موجود است → **برای دیپلوی Worker چیز جدیدی لازم نداریم، فقط استفادهٔ مجدد.**
- نزدیک‌ترین الگو: فیچر «DNS اختصاصی» ([dedicated-dns-manager.js](../dedicated-dns-manager.js) + [dedidns.js](../public/components/dedidns.js)).

### ۱-۲) اپ اندروید خودمان (`G:\ip scanner\android`) — **مرجع اصلی ما**
از قبل ماژول GST کامل دارد و ویندوز باید پورت همان باشد:

| فایل اندروید | نقش |
|---|---|
| `engines/gst/GstConfigManager.kt` | لیست ریلی‌ها (`GstRelay{id, deploymentId, authKey}`)، لیست SNI، لیست IP تمیز |
| `engines/gst/GstAutoDeployer.kt` | دیپلوی **کاملاً خودکار** Apps Script از طریق `script.googleapis.com` با OAuth |
| `engines/gst/GstDiagnostics.kt` | تست واقعی ریلی (probe به `gstatic.com/generate_204` از داخل ریلی) |
| `engines/gst/GstEngine.kt` | هستهٔ Rust از طریق JNI |
| `ui/emergency/GstSetupWizard.kt` | ویزارد ۵ مرحله‌ای فارسی |
| `assets/gst/Code.js` (۷۹۷ خط) | اسکریپت گوگل |
| `assets/gst_relay_worker.js` (۱۱۷ خط) | Worker کلادفلر |

### ۱-۳) پروژهٔ `mhr-cfw-main` (پایتون، گوگل‌اسکریپت + کلادفلر)
- زنجیره: مرورگر → پروکسی محلی (MITM) → TLS به IP گوگل با `SNI=www.google.com` → Apps Script → Cloudflare Worker → مقصد.
- پروتکل سیم: `{k,m,u,h,b,ct,r}` → `{s,h,b}` (بدنه base64).
- نکات قابل برداشت: `chunked_download_*` (دانلود موازی تکه‌ای)، `direct_google_exclude/allow`، `bypass_hosts`، `google_ip_scanner.py`، `cert_installer.py`.
- ضعف‌ها: تک‌ریلی، بدون UI، پیکربندی دستی JSON، بدون تست واقعی.

### ۱-۴) پروژهٔ `MasterHttpRelayVPN-RUST-main` (Rust، ~۲۹ هزار خط)
همان هسته‌ای که اپ اندروید ما از آن استفاده می‌کند. امکانات کلیدی:
- **چند ریلی واقعی**: `script_ids` به‌جای `script_id`، به‌علاوهٔ auto-blacklist (strikes/window/cooldown) و چرخش.
- `quota_tracker.rs`: سهمیهٔ روزانهٔ هر اکانت گوگل جدا شمرده می‌شود.
- `scan_ips.rs` / `scan_sni.rs`: اسکن IP تمیز گوگل و اسکن SNI عبورپذیر.
- `cert_installer.rs` (۲۰۴۰ خط): نصب/حذف CA در ویندوز + NSS مرورگرها.
- `fronting_groups`: گروه‌های دامنه‌فرانتینگ (Vercel/Fastly/CloudFront/GitHub…).
- سه حالت: `apps_script` / `full` (tunnel-node، TCP+UDP خام) / `direct` (فقط SNI-rewrite).

**نتیجه‌گیری:** هستهٔ Rust را دوباره نمی‌نویسیم. آن را در پروژه vendor می‌کنیم، برای ویندوز بیلد می‌گیریم (`core/gst.exe`) و نرم‌افزار ما آن را مثل `xray.exe` مدیریت می‌کند.

## ۲) معماری پیشنهادی

```
مرورگر / TUN
     │
     ▼
gst.exe  (هستهٔ Rust — HTTP 8085 / SOCKS5 8086)
     │  MITM محلی با CA خودمان
     ▼
TLS به «IP تمیز گوگل» با SNI جعلی    ← اسکن‌شده و تست‌شده
     │
     ▼
ریلی ۱ … ریلی ۱۰  (Google Apps Script)   ← چرخش + auto-blacklist + سهمیه
     │                    │
     │ (اگر CF خاموش)     │ (اگر CF روشنِ همان ریلی)
     ▼                    ▼
   مقصد          Cloudflare Worker اختصاصی همان ریلی → مقصد
```

**قاعدهٔ طلایی:** Cloudflare یک سوییچ **per-relay** است. هر ریلی مستقلاً یکی از این دو حالت را دارد:
- `mode: "direct"` → `WORKER_URL` در اسکریپت گوگل خالی است؛ خود Apps Script فچ می‌کند.
- `mode: "cf"` → `WORKER_URL` مقدار دارد؛ Apps Script فقط auth+forward می‌کند.

اگر Worker یک ریلی خطا داد، هسته آن ریلی را موقتاً کنار می‌گذارد و از ریلی‌های سالم دیگر استفاده می‌کند (نه اینکه کل تونل بیفتد).

### ۲-۱) پاسخ سؤال «اطلاعات کدام طرف در کدام باید باشد؟»
بررسی کد هر دو پروژه پاسخ را قطعی می‌کند: **جریان یک‌طرفه است.**
- اسکریپت گوگل باید `WORKER_URL` را بداند (آدرس Worker).
- Worker **نیازی به دانستن چیزی از گوگل ندارد** — فقط `AUTH_KEY` مشترک.
- کلاینت ویندوز باید بداند: `deploymentId` + `authKey`.

پس ترتیب اجباری مراحل: **اول Worker ساخته می‌شود، بعد آدرسش داخل اسکریپت گوگل تزریق می‌شود.** ویزارد ما همین ترتیب را تحمیل می‌کند تا کاربر گیر نکند.

## ۳-۵) اصلاح مهم — «یک Worker، دو کار»

> ⚠️ اصلاحیه نسبت به نسخهٔ اول سند: `gst_relay_worker.js` در **اپ اندروید ما برای ترکیب نیست** — آنجا یک ریلی موازیِ ضدتحریم است. آن را مرجع معماری ترکیبی نمی‌گیریم.

اما با خواندن کدش یک نکتهٔ کلیدی روشن شد: **آن Worker دقیقاً همان پروتکل `{k,u,m,h,b}` را حرف می‌زند که Worker ترکیبی هم نیاز دارد.** یعنی از نظر کد، هر دو کار یک چیزند: «یک fetch-proxy احراز هویت‌شده روی لبهٔ کلادفلر».

پس در ویندوز **دو Worker جدا نمی‌سازیم.** هر ریلی **یک Worker** دارد که همزمان دو نقش را بازی می‌کند:

| نقش | چه‌وقت | مسیر |
|---|---|---|
| **الف) ضدتحریم** | فقط هنگام راه‌اندازی | پنل ویندوز → Worker کاربر → `script.google.com` |
| **ب) شتاب‌دهنده** | هنگام استفادهٔ عادی | Apps Script → Worker کاربر → سایت مقصد |

**چرا این بهتر است:**
- وابستگی به رلهٔ امارات از بین می‌رود — اگر بعداً آن سیستم را برداریم، اینجا دوباره‌کاری نداریم (خواستهٔ صریح).
- کاربر فقط **یک بار** یک Worker می‌سازد، نه دو بار. گیج نمی‌شود.
- ضدتحریم روی کلادفلرِ **خود کاربر** است، نه سرور مشترک → سریع‌تر و خصوصی‌تر.
- کد Worker یکی است → نگهداری ساده‌تر.

**فایل واحد:** `public/gst/relay_worker.js`

### ترتیب اجباری که از این نتیجه می‌شود
```
۱. اعتبارنامهٔ کلادفلر (از پنل ابری موجود)
        ↓
۲. ساخت Worker  ← اینجا هنوز به گوگل نیاز نداریم، پس تحریم مانع نیست
        ↓
۳. Worker روشن است → حالا از داخلش می‌توانیم script.google.com را باز کنیم
        ↓
۴. ساخت اسکریپت گوگل (با WORKER_URL از پیش تزریق‌شده)
        ↓
۵. کاربر تصمیم می‌گیرد Worker در مسیر داده بماند یا نه (سوییچ per-relay)
```
مرحلهٔ ۲ قبل از هر تماسی با گوگل انجام می‌شود، پس مشکل مرغ-و-تخم‌مرغ نداریم. `api.cloudflare.com` از ایران تحریم نیست.

### حالت «بدون کلادفلر» چه می‌شود؟
کاربری که اصلاً کلادفلر نمی‌خواهد، همچنان باید یک‌بار به `script.google.com` برسد. برای او **تحریم‌شکن موجود (رلهٔ امارات)** به‌عنوان مسیر پشتیبان می‌ماند. یعنی:

| وضعیت کاربر | مسیر ضدتحریم در راه‌اندازی |
|---|---|
| کلادفلر دارد (حالت «سریع») | Worker خودش — **پیش‌فرض و توصیه‌شده** |
| کلادفلر ندارد (حالت «ساده») | تحریم‌شکن امارات — پشتیبان |
| هیچ‌کدام کار نکرد | راهنمای دستی («با VPN دیگری فقط این یک صفحه را باز کنید») |

و مهم‌ترین نکته: **بعد از راه‌اندازی، تونل مستقل کار می‌کند.** ضدتحریم فقط برای همان چند دقیقهٔ ساخت اسکریپت لازم است.

## ۴) ویزارد مرحله‌ای — هر مرحله فقط یک کار

۷ مرحله در حالت «سریع»، ۶ مرحله در حالت «ساده». کاربر هیچ‌وقت بیش از یک تصمیم در هر صفحه ندارد.

| # | عنوان | کاری که انجام می‌شود | خودکار؟ |
|---|---|---|---|
| ۱ | **خوش‌آمد و انتخاب حالت** | دو کارت بزرگ: «سریع (توصیه‌شده) — با کلادفلر خودت» یا «ساده — فقط گوگل». زیر هرکدام یک جملهٔ فارسی ساده | — |
| ۲ | **گواهی امنیتی** | ساخت CA + نصب خودکار در Trust Store ویندوز + تأیید واقعی نصب | ✅ کاملاً خودکار |
| ۳ | **رمز ریلی** | تولید **خودکار** کلید ۳۲ کاراکتری. کاربر فقط می‌بیند؛ دکمهٔ «تولید مجدد» | ✅ کاملاً خودکار |
| ۴ | **Worker کلادفلر** | *فقط حالت سریع.* انتخاب اکانت از ماژول ابری → دیپلوی → **تست واقعی**. این Worker از همین‌جا نقش ضدتحریم هم می‌گیرد | ✅ کاملاً خودکار |
| ۵ | **باز کردن راه گوگل** | خودکار بررسی می‌کند `script.google.com` قابل دسترسی است یا نه، و اگر نه خودش مسیر ضدتحریم را برقرار می‌کند (جزئیات ۴-۱) | ✅ کاملاً خودکار |
| ۶ | **ساخت اسکریپت گوگل** | اسکریپت آماده (`AUTH_KEY` و `WORKER_URL` از پیش تزریق‌شده) با یک دکمه کپی می‌شود؛ راهنمای تصویری ۶ قدمی؛ کاربر Deployment ID را برمی‌گرداند و **تست واقعی ریلی** همان‌جا اجرا می‌شود | دستی + تست خودکار |
| ۷ | **آماده است** | اسکن خودکار IP/SNI در پس‌زمینه + خلاصه + دکمهٔ اتصال. مسیر ضدتحریم **خودکار** به حالت قبل برمی‌گردد | ✅ |

مرحلهٔ ۴ در حالت «ساده» حذف می‌شود.

### ۴-۱) مرحلهٔ ۵ — «باز کردن راه گوگل» بدون گیج کردن کاربر
کاربر هیچ‌وقت کلمهٔ «تحریم‌شکن» را به‌عنوان یک تصمیم نمی‌بیند. پنل فقط می‌گوید **«در حال باز کردن راه دسترسی به گوگل…»** و پشت صحنه به ترتیب امتحان می‌کند:

۱. **تست مستقیم** — شاید اینترنت کاربر اصلاً مشکلی ندارد → سبز، ادامه.
۲. **از طریق Worker خود کاربر** (حالت سریع) — درخواست به `script.google.com` از داخل Worker → پیش‌فرض و سریع‌ترین.
۳. **تحریم‌شکن امارات** (حالت ساده) — `/api/sanction/enable` با افزودن خودکار `script.google.com` و `script.googleusercontent.com` به لیست دامنه‌ها.
۴. **شکست هر سه** → پیام فارسی روشن: «فعلاً نمی‌توانیم به گوگل برسیم. اگر VPN دیگری دارید یک لحظه روشن کنید و دکمهٔ تلاش مجدد را بزنید.»

وضعیت اولیهٔ تحریم‌شکن ذخیره می‌شود و در مرحلهٔ ۷ **بی‌صدا** بازگردانده می‌شود — اگر کاربر خودش از قبل روشنش کرده بود، دست‌نخورده می‌ماند. هیچ سؤال اضافه‌ای از کاربر پرسیده نمی‌شود.

هر ۴ تلاش با متن فارسی در لاگ هسته ثبت می‌شود تا اگر گیر کرد دقیقاً بدانیم کجا.

### ۴-۲) افزودن ریلی دوم به بعد
مراحل ۲، ۵ و ۷ رد می‌شوند (قبلاً انجام شده و راه گوگل باز است). می‌ماند: رمز → Worker → اسکریپت. یعنی **۳ مرحله**.

### ۴-۳) روشن کردن کلادفلر برای ریلیِ از قبل ساخته‌شده
ویزارد ۲ مرحله‌ای: Worker بساز → آدرسش را در اسکریپت گوگلِ همان ریلی جای‌گذاری کن (فقط یک خط تغییر می‌کند و پنل دقیقاً همان یک خط را نشان می‌دهد).

### ۵-۱) تب «ریلی‌ها» — بی‌نهایت حساب

```
┌──────────────────────────────────────────────────┐
```

- **درون‌ریزی/برون‌ریزی**: کل مجموعه به یک لینک `gst://` رمزنگاری‌شده تبدیل می‌شود.


**تفکیک گوگل از کلادفلر** (خواستهٔ صریح) — هر ریلی **دو چراغ مستقل** دارد، چون دو نقطهٔ خرابی مستقل‌اند:

| گوگل | کلادفلر | تشخیص و رفتار سیستم |
|---|---|---|
| ● | ● | سالم |
| ● | ✕ | «Worker خراب است، ریلی روی مسیر مستقیم کار می‌کند» → **خودکار** موقتاً CF را دور می‌زند، تونل قطع نمی‌شود |
| ✕ | ● | «اسکریپت گوگل خراب است» — Worker سالم بودنش بی‌فایده است؛ ریلی از چرخش خارج می‌شود |
| ✕ | ✕ | ریلی کاملاً خارج + دکمهٔ «ساخت مجدد» |

روش تشخیص تفکیکی: دو probe جدا زده می‌شود — یکی **مستقیم به Worker** (`*.workers.dev`) و یکی **به Apps Script**. مقایسهٔ نتیجه دقیقاً می‌گوید کدام طرف خراب است.

**تشخیص «پر شدن سهمیه»** جدا از «قطعی» است:
- گوگل: خطای `Service invoked too many times` یا `Exceeded maximum execution time` → «سهمیهٔ امروز تمام شد، ساعت X بامداد ریست می‌شود» + شمارش معکوس.
- کلادفلر: کد `1015`/`1013` یا HTTP 429 → «سهمیهٔ Worker».
- شمارندهٔ محلی (پورت `quota_tracker.rs`) قبل از رسیدن به سقف در ۸۰٪ هشدار می‌دهد.

**بررسی خودکار دوره‌ای**: هر ۵ دقیقه در پس‌زمینه، بی‌صدا. اگر چیزی خراب شد، نقطهٔ قرمز روی آیکون activity-bar + یک اعلان فارسی.

هر خطا **کد + یک راه‌حل فارسی مشخص + یک دکمهٔ اقدام** دارد. هیچ خطای خامی به کاربر نشان داده نمی‌شود.

- تیک‌ها یعنی «از اینها استفاده کن» — هسته بینشان می‌چرخد، پس چند انتخاب = پایداری بیشتر.
- **انتخاب خودکار**: بهترین ۵ مورد را بر اساس تأخیر واقعی تیک می‌زند.

- افزودن دستی برای کاربر حرفه‌ای.
- **بهینه‌سازی خودکار** (اختیاری، پیش‌فرض روشن): هر ۱۰ دقیقه بی‌صدا می‌سنجد و اگر مسیر بهتری پیدا شد جابه‌جا می‌شود.

## ۶-۵) سه حالت اتصال — دقیقاً مثل پنل Aether/وایرگارد

پنل GST همان الگوی [aether.js](../public/components/aether.js) را می‌گیرد: یک دکمهٔ اتصال + دو سوییچ مستقل.

| حالت | چه می‌شود | کاربرد |
|---|---|---|
| **۱ — فقط تونل (بدون پروکسی سیستم)** | `gst.exe` روشن است و روی `127.0.0.1:8085` (HTTP) و `:8086` (SOCKS5) گوش می‌دهد. هیچ تغییری در ویندوز داده نمی‌شود | کاربر خودش مرورگر/تلگرام را دستی تنظیم می‌کند؛ سبک‌ترین حالت |
| **۲ — پروکسی سیستم روشن** | همان بالا + ثبت پروکسی در رجیستری ویندوز (`/api/proxy/system` موجود) | کار عادی روزمره؛ فقط برنامه‌های proxy-aware |
| **۳ — تونل سراسری (TUN)** | همان بالا + `sing-box.exe` با `wintun.dll` روی SOCKS خود GST. **بدون هیچ نشتی** — QUIC، WebRTC، بازی‌ها، همه‌چیز | حالت امن کامل |

جزئیات پیاده‌سازی: یک کپی از [core/tun-config.json](../core/tun-config.json) ساخته می‌شود که `outbounds[0].server_port` را به پورت SOCKS خود GST می‌بندد و در `route.rules` پروسهٔ `gst.exe` را `direct` می‌کند (جلوگیری از حلقه) — دقیقاً همان کاری که الان برای `aether.exe` انجام می‌شود.

## ۶-۶) همزیستی با موتورهای دیگر — تصمیم

بررسی کد نشان می‌دهد **دیتاپلین باید انحصاری باشد** و این هم سبک‌تر است هم سریع‌تر:

- `tun-manager.js` تنها **یک** خروجی SOCKS در `tun-config.json` دارد و `auto_route` مسیر پیش‌فرض ویندوز را می‌گیرد. دو موتور همزمان یعنی جنگ بر سر جدول مسیریابی → نشت و افت سرعت.
- زنجیر کردن GST پشت Xray یعنی دو بار رمزنگاری و دو hop اضافه → تأخیر چند برابر. هیچ سودی ندارد چون GST خودش دامنه‌فرانتینگ کامل دارد.

**پس:** روشن کردن GST به‌صورت خودکار Xray/Aether را خاموش می‌کند (با پیام فارسی روشن: «موتور Aether خاموش شد تا تونل گوگل اسکریپت با بیشترین سرعت کار کند»)، و برعکس.

**استثناها که همزمان کار می‌کنند** (چون لایهٔ متفاوتی هستند و تداخل ندارند):
- **تحریم‌شکن** — لازم است، به‌ویژه در مرحلهٔ ۵ ویزارد.
- **DNS اختصاصی** — می‌تواند resolver خود GST شود (ضد نشت بهتر).
- **اسکنر IP** — فقط داده تولید می‌کند.

## ۶-۷) تعمیر و راهنمایی — هیچ خطای بن‌بستی وجود ندارد

قاعده: **هر خطایی که سیستم تشخیص می‌دهد، باید یک دکمهٔ اقدام و یک جملهٔ فارسی داشته باشد.** کاربر هرگز با یک چراغ قرمز و بدون راه‌حل تنها گذاشته نمی‌شود.

### ۶-۷-۱) جدول تشخیص و تعمیر

| خطا | چه اتفاقی افتاده | راهنمایی فارسی | دکمهٔ اقدام |
|---|---|---|---|
| **گواهی نصب نیست / نامعتبر** | CA از Trust Store پاک شده یا منقضی است | «گواهی امنیتی نصب نیست، سایت‌های https باز نمی‌شوند» | **[نصب مجدد]** — یک کلیک، خودکار با ارتقای دسترسی |
| **گواهی هست ولی مرورگر قبول نمی‌کند** | فایرفاکس/کروم NSS store جدا دارد | «مرورگر فایرفاکس گواهی را جدا نگه می‌دارد» | **[نصب در مرورگرها]** |
| **ریلی گوگل — خطای ۴۰۱/۴۰۳** | دیپلوی روی «Only myself» مانده یا Authorize نشده | «هنگام Deploy گزینهٔ Anyone انتخاب نشده» + تصویر همان صفحه | **[راهنمای گام‌به‌گام]** → ویزارد مینی |
| **ریلی گوگل — رمز اشتباه** | `AUTH_KEY` اسکریپت با برنامه فرق دارد | «رمز داخل اسکریپت با برنامه یکی نیست» | **[کپی رمز درست]** + **[کپی اسکریپت اصلاح‌شده]** |
| **ریلی گوگل — HTML به‌جای JSON** | دیپلوی حذف شده یا آدرس اشتباه است | «این دیپلویمنت دیگر وجود ندارد» | **[ساخت مجدد اسکریپت]** |
| **ریلی گوگل — سهمیه تمام** | سقف روزانهٔ حساب | «سهمیهٔ این حساب گوگل تمام شد» + شمارش معکوس تا ریست | **[استفاده از ریلی دیگر]** / **[+ افزودن حساب]** |
| **کلادفلر — Worker پیدا نشد** | حذف شده از داشبورد | «Worker روی حساب شما نیست» | **[ساخت مجدد Worker]** — یک کلیک، کاملاً خودکار |
| **کلادفلر — خطای احراز هویت** | Global API Key عوض شده | «کلید کلادفلر معتبر نیست» | **[اصلاح در پنل ابری]** — مستقیم به همان پنل |
| **کلادفلر — سهمیه تمام (۱۰۱۵/۱۰۱۳/۴۲۹)** | سقف روزانهٔ Worker | «سهمیهٔ Worker امروز تمام شد» + شمارش معکوس | **[موقتاً خاموش کن]** (ریلی روی مسیر مستقیم ادامه می‌دهد) |
| **کلادفلر خراب، گوگل سالم** | فقط پای Worker می‌لنگد | «Worker خراب است ولی نگران نباشید — این ریلی روی مسیر مستقیم کار می‌کند» | خودکار انجام شده، فقط اطلاع |
| **راه گوگل بسته** | تحریم | «فعلاً به گوگل نمی‌رسیم» | **[تلاش مجدد]** با زنجیرهٔ ۴ مرحله‌ای بخش ۴-۱ |

### ۶-۷-۲) زمان ریست سهمیه‌ها — نکتهٔ مهم

⚠️ **یک اصلاح فنی:** ساعت ۰۳:۳۰ بامداد به وقت ایران **فقط برای کلادفلر** درست است (کلادفلر روی نیمه‌شب UTC ریست می‌کند = ۰۳:۳۰ ایران). **گوگل روی نیمه‌شب وقت اقیانوس آرام (Pacific) ریست می‌کند**، که به وقت ایران حدود **۱۱:۳۰ صبح** می‌شود — و چون آمریکا ساعت تابستانی دارد، فصلی یک ساعت جابه‌جا می‌شود (۱۰:۳۰ در تابستان).

به همین دلیل عدد را **hardcode نمی‌کنیم**؛ `gst-quota.js` آن را زنده حساب می‌کند:
```
ریست کلادفلر = نیمه‌شب UTC        → به وقت ایران نمایش داده می‌شود
ریست گوگل    = نیمه‌شب America/Los_Angeles → به وقت ایران نمایش داده می‌شود
```
و در پنل به‌صورت انسانی نشان داده می‌شود: «سهمیهٔ گوگل ۴ ساعت و ۱۲ دقیقهٔ دیگر (۱۱:۳۰ صبح) ریست می‌شود».

اگر تو مطمئنی که در عمل گوگل هم ۰۳:۳۰ ریست می‌شود، بگو تا همان را بگذارم — ولی پیشنهادم محاسبهٔ زنده است چون در هر دو حالت درست درمی‌آید.

### ۶-۷-۳) تقسیم بار بین حساب‌ها — کلید دیرتر تمام شدن سهمیه

دقیقاً مثل `MasterHttpRelayVPN-RUST`: هسته `script_ids` را به‌صورت آرایه می‌گیرد و بار را بین همه پخش می‌کند.

- **۱۰ حساب گوگل ≈ ۱۰ برابر سهمیه.** پنل این را صریح به کاربر می‌گوید: «با ۳ حساب فعلی روزانه حدود X درخواست دارید — با افزودن حساب چهارم به Y می‌رسید.»
- **auto-blacklist**: ریلی‌ای که پشت‌سرهم خطا بدهد موقتاً از چرخش خارج می‌شود (`strikes` / `window` / `cooldown`) و بعد خودش برمی‌گردد. تونل قطع نمی‌شود.
- **پخش هوشمند، نه صرفاً round-robin**: وزن هر ریلی بر اساس تأخیر واقعی و سهمیهٔ باقی‌مانده تعیین می‌شود. ریلی‌ای که به ۸۰٪ سهمیه رسیده وزنش کم می‌شود تا برای مواقع اضطراری ذخیره بماند.
- **پیش‌بینی**: پنل بر اساس مصرف فعلی می‌گوید «با این سرعت مصرف، سهمیهٔ امروز تا ساعت ۲۱ تمام می‌شود».

### ۶-۷-۴) دکمهٔ «تست همه» با n حساب

با ۱۰ ریلی، **۲۰ probe** زده می‌شود (برای هر ریلی یکی به گوگل و یکی به کلادفلر)، به‌صورت **موازی** با سقف همزمانی ۶ تا، و نتیجه به‌صورت زنده ردیف‌به‌ردیف پر می‌شود:

```

─────────────────────────────────────────────────────
۱ «شخصی»    گوگل ● ۲۴۰ms      کلادفلر ● ۳۸ms     سالم

۳ «سوم»     گوگل ✕ ۴۰۱        کلادفلر ● ۴۱ms     ✕ اسکریپت گوگل

خلاصه: ۷ سالم · ۱ سهمیه گوگل · ۱ سهمیه کلادفلر · ۱ خراب
```

هر ردیف **صراحتاً می‌گوید کدام پا خراب است**، و ردیف‌های خراب زیرشان یک خط راهنمایی + دکمهٔ اقدام می‌گیرند. کل خروجی هم‌زمان با متن فارسی در لاگ هسته ثبت می‌شود.

---

## ۷) ضد نشت (خواستهٔ صریح)

۱. تمام DNS از داخل تونل (`gst.exe` خودش resolve می‌کند) — سیستم هرگز مستقیم query نمی‌زند.
۲. اختیاری: اتصال به فیچر موجود «DNS اختصاصی» به‌عنوان resolver.
۳. حالت TUN با kill-switch: اگر هسته بمیرد، مسیر پیش‌فرض بازنمی‌گردد تا کاربر تأیید کند.
۴. `bypass_hosts` فقط برای `localhost`/`.local`/`.lan`.
۵. جلوگیری از حلقه: دامنه‌های خودِ ریلی و Worker همیشه مستقیم.
۶. WebRTC/IPv6 leak: IPv6 در حالت TUN بسته می‌شود.

---

## ۸) لاگ‌گذاری

هر مرحله یک شناسهٔ لاگ می‌گیرد و در **لاگ هسته** با پیشوند `[GST]` و متن فارسی می‌نشیند:
```

[GST][۰۲] نصب در Trust Store ویندوز… موفق ✓
[GST][۰۴] دیپلوی Worker روی اکانت user@mail.com…
[GST][۰۴] ✗ خطا ۱۰۰۰۰: توکن معتبر نیست — Global API Key را بررسی کنید
[GST][۰۶] تست ریلی «شخصی»: HTTP 204، ۲۴۰ms، IP خروجی 34.x.x.x ✓
```
کلیدهای حساس همیشه redact می‌شوند (`AKfy…9dQ2`).

## ۹) چیزهایی که ما را از هر دو پروژه بالاتر می‌برد

۱. **دیپلوی کاملاً خودکار سمت کلادفلر** — mhr-cfw کاملاً دستی است. سمت گوگل عمداً دستی می‌ماند (API گوگل حساس است و به محدودیت می‌خوریم)، ولی با اسکریپت از پیش آماده و راهنمای تصویری تا حد ممکن بی‌دردسر.
۲. **سوییچ کلادفلر per-relay** — هیچ‌کدام ندارند. **در اپ اندروید خودمان هم نیست** — این اولین جایی است که داریمش.
۲-۱. **رفع خودکار مانع تحریم گوگل** با تحریم‌شکن داخلی — هیچ ابزار دیگری این را ندارد.
۳. **ترکیب با فیچرهای موجود خودمان**: IP تمیز از اسکنر، DNS اختصاصی، تحریم‌شکن، SNI.
۴. **مانیتور سهمیهٔ زنده** برای هر اکانت گوگل + هشدار قبل از اتمام + جابه‌جایی خودکار.
۵. **خودترمیمی**: ریلی خراب خودکار کنار می‌رود، سالم می‌شود، برمی‌گردد.
۶. **پشتیبان‌گیری/بازیابی و اشتراک‌گذاری پیکربندی** با یک لینک `gst://` رمزنگاری‌شده (کاربر می‌تواند ۱۰ ریلی‌اش را به دوستش بدهد).
۷. **بهینه‌سازی خودکار**: هر ۱۰ دقیقه IP/SNI را بی‌صدا می‌سنجد و بهترین را انتخاب می‌کند.
۸. **دانلود موازی تکه‌ای** (از `chunked_download_*` پایتون) برای سرعت چند برابری فایل‌های بزرگ.
۹. **گروه‌های دامنه‌فرانتینگ** (Vercel/Fastly/GitHub) از پروژهٔ Rust — مسیرهای جایگزین وقتی گوگل هم فیلتر شد.
۱۰. **صفحهٔ عیب‌یابی هوشمند**: هر کد خطا یک راه‌حل فارسی مشخص دارد.
